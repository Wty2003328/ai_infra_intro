# Storage and Model Loading

Model weights and checkpoints are the heaviest data objects in AI infra. A 70B model is 140 GB. A training checkpoint is multiples of that. A 400B MoE model can be 800+ GB. Getting these bytes in and out of GPUs without wrecking your latency SLOs or your capacity plan is its own engineering discipline.

---

## 1. The Storage Stack for AI Workloads

```
    ┌─────────────────────────────────────────────┐
    │ Object Storage (S3, GCS, R2, MinIO)         │
    │  • Cheap ($20-30/TB-month warm)             │
    │  • 10-100 Gbps per bucket                   │
    │  • Long-term / cold data                    │
    └────────────────────┬────────────────────────┘
                         │ sync once
    ┌────────────────────▼────────────────────────┐
    │ Parallel Filesystem (Lustre, WekaFS, DAOS)  │
    │  • ~100 GB/s aggregate per cluster          │
    │  • Shared across all nodes                  │
    │  • Hot training data, active checkpoints    │
    └────────────────────┬────────────────────────┘
                         │ read/cache
    ┌────────────────────▼────────────────────────┐
    │ Node-local NVMe                             │
    │  • 7-14 GB/s per drive, 50+ GB/s aggregate  │
    │  • Model weights cache, scratch             │
    └────────────────────┬────────────────────────┘
                         │ load (GDS or cpu-bounce)
    ┌────────────────────▼────────────────────────┐
    │ CPU Host Memory (512 GB - 2 TB DDR5)        │
    │  • ~300 GB/s aggregate                      │
    │  • Pinned buffers, optimizer states         │
    └────────────────────┬────────────────────────┘
                         │ H2D cudaMemcpy / NVLink-C2C
    ┌────────────────────▼────────────────────────┐
    │ GPU HBM (80-288 GB)                         │
    │  • 3.35-12 TB/s                             │
    │  • Live weights, KV cache, activations      │
    └─────────────────────────────────────────────┘
```

## 2. Model Weight Formats

### 2.1 Safetensors (the standard in 2026)

**Design goals:** safe (no arbitrary code execution), fast to load (memory-mappable), simple format.

**Layout:**
- 8-byte little-endian header length N
- N-byte JSON header describing each tensor: name, dtype, shape, data offset, data length
- Concatenated raw tensor bytes

```
┌────────────────┬─────────────────────┬──────────────────────────┐
│ N (8B LE u64)  │ JSON header (N B)   │ Raw tensor data (bytes)  │
└────────────────┴─────────────────────┴──────────────────────────┘
```

**Why it replaced PyTorch's `torch.save`:**
- `torch.save` uses Python pickle → arbitrary code execution risk
- `torch.save` requires parsing Python objects → slow
- Safetensors is `mmap`-able: the kernel maps the file into virtual memory; pages fault in on-demand

**Loading pattern:**
```python
from safetensors.torch import load_file

# mmap-backed; tensors share memory with the file
state_dict = load_file("model.safetensors", device="cuda:0")
```

Under the hood, safetensors does one `open` + `mmap` + parsing of the header (tiny), then creates `torch.Tensor` views over the mapped region. If CUDA direct loading is available, it copies directly from the mapped region to GPU without a user-space bounce.

### 2.2 GGUF

Developed for llama.cpp. Includes metadata (model architecture, tokenizer config, quantization parameters) inline, so a single .gguf file is self-describing.

**Notable features:**
- Multiple quantization types (Q4_K_M, Q5_K_S, etc. — k-quant formats with block-wise scales)
- Built-in tokenizer data
- Version field with strict schema evolution

Used primarily in CPU/consumer-GPU inference (llama.cpp, Ollama, LM Studio). Production server frameworks prefer safetensors.

### 2.3 TensorRT engine files (.plan)

Pre-compiled, GPU-specific, not portable across hardware. Contains:
- Kernel code specialized for your GPU
- Layer fusion decisions
- Selected attention implementations
- Quantization calibration data

Generated by TensorRT-LLM's build step. Fastest inference but opaque (can't inspect weights), hardware-locked, and rebuilds on GPU change.

### 2.4 HuggingFace-style sharded safetensors

Large models are sharded across multiple files:
```
model-00001-of-00014.safetensors
model-00002-of-00014.safetensors
...
model-00014-of-00014.safetensors
model.safetensors.index.json    ← maps tensor names to shards
```

Rationale: per-shard file size of 5-10 GB fits in typical HTTP range requests, allows parallel downloads, and avoids the S3 5 GB single-part upload limit.

## 3. The Model Loading Pipeline

### 3.1 Cold load path (first time)

```
S3 bucket
  │  HTTP/HTTPS GET, 10-100 Gbps per connection
  ▼
Node NVMe (~10 TB SSD pool)
  │  mmap() or posix_read()
  ▼
CPU host memory (page cache)
  │  cudaMemcpy HtoD  (or GDS bypass)
  ▼
GPU HBM
```

For a 140 GB model:
- S3 → NVMe at 10 Gbps = 112 s (network-bound)
- NVMe → CPU at 7 GB/s = 20 s
- CPU → GPU at 64 GB/s (PCIe Gen5) = 2.2 s
- **Total cold load: ~135 s**

This is the infamous "GPU pod takes 2 minutes to come up" problem. Every scale-up event pays this cost.

### 3.2 Warm load path (NVMe cache hit)

Skip the S3 download; the model is already on NVMe from a previous pod.

- NVMe → CPU: 20 s
- CPU → GPU: 2 s
- **Total: ~22 s**

### 3.3 Hot load path (page cache hit)

If the previous tenant on this node loaded the same model and it's still in OS page cache:

- CPU → GPU: 2-3 s
- **Total: ~3 s**

### 3.4 GDS (GPUDirect Storage) path

Skip CPU host memory entirely; NVMe DMA directly into GPU HBM.

- NVMe → GPU: bounded by min(NVMe BW, PCIe BW) = min(14 GB/s, 64 GB/s) = 14 GB/s per drive
- 140 GB / 14 GB/s = 10 s on one drive; parallel across 4 drives = ~3 s

GDS requires:
- NVIDIA `nvidia-fs` kernel module
- Compatible filesystem (XFS, ext4 in GDS mode, or WekaFS)
- PCIe peer-to-peer enabled between GPU and NVMe controller

## 4. Node-Local NVMe Caching Strategies

### 4.1 The tradeoff

NVMe is fast but finite (say 10 TB per node). In a multi-tenant cluster with many models, you can't cache every model on every node.

### 4.2 Strategies

**Eager pre-pull:** at pod scheduling, download the model to NVMe before reporting ready. Adds startup latency but avoids cold-path on first request.

**Lazy pre-pull:** pod starts; downloads model in background; serves requests from partial pages as they arrive. Complex; prone to timeouts on first requests.

**Tiered cache (LRU):** maintain an LRU over models, evict oldest when disk is full. Needs coordination with scheduler to prefer nodes with matching cache entries.

**Pre-provisioned PVC:** Kubernetes PersistentVolumeClaim pre-loaded with weights; pods mount it read-only. Fast, but rigid — every pod on the node shares the PVC.

### 4.3 Node affinity with cache awareness

Modern Kubernetes operators (OME, llm-d) track which models are cached on which nodes and bias scheduler toward cache-hot placements:

```yaml
# Pseudo-yaml for an OME-style model-aware scheduling hint
affinity:
  nodeAffinity:
    preferredDuringSchedulingIgnoredDuringExecution:
    - preference:
        matchExpressions:
        - key: ome.nvidia.com/cached-model
          operator: In
          values: ["llama-3-70b"]
      weight: 100
```

## 5. Parallel Filesystems for AI

### 5.1 Lustre

Open-source, originally HPC. Widely deployed. Architecture: MDS (metadata server) + OSTs (object storage targets) + clients.

- Bandwidth: 100s of GB/s aggregate
- Latency: milliseconds for metadata ops (high by AI standards)
- Pain point: MDS is a bottleneck for small-file workloads

### 5.2 WekaFS

Commercial, designed for AI. NVMe-based, POSIX-compliant, runs in userspace via SPDK.

- Aggregate BW: up to 1 TB/s in large deployments
- Metadata: distributed, no single bottleneck
- POSIX + S3 + NFS + SMB + GPUDirect support
- Cost: significantly more than Lustre per TB

### 5.3 DAOS (Distributed Asynchronous Object Storage)

Intel-developed, Optane/PMEM-optimized. Best raw performance; niche adoption.

### 5.4 HPC vs AI filesystem differences

HPC workloads: few massive files, mostly writes (checkpoints).
AI workloads: many tiny files (training data), massive concurrent reads, bursty checkpoint writes.

Lustre was designed for the former. Modern AI filesystems optimize for the latter — especially the metadata-heavy dataloader pattern (each training worker opens thousands of small samples per epoch).

## 6. Dataloading for Training

### 6.1 The critical path

Per training step:
1. Dataloader worker processes read samples from storage
2. Decode (JPEG decompress, tokenize, etc.)
3. Collate into a batch
4. Transfer to GPU
5. GPU consumes

If any stage is slower than the GPU compute time, GPUs stall waiting for data. Modern transformers can eat 4K tokens per batch per step, and at 10 K tokens/s per GPU that's 40 K samples/s total. If samples are 10 KB average, that's 400 MB/s per GPU — 3.2 GB/s per 8-GPU node.

### 6.2 Patterns

**WebDataset / tar shards:** pack many small samples into tar files, stream sequentially. Eliminates metadata overhead.

**Mosaic Streaming / StreamingDataset:** cloud-native streaming. Shards hosted on S3; clients prefetch and decompress.

**NVIDIA DALI:** GPU-accelerated dataloading. Decode (esp. images) happens on the GPU's copy engine or on dedicated NVDEC units.

**Iterable datasets with sharding:** each DP rank reads a distinct shard range; no cross-rank coordination needed.

### 6.3 Dataloader parallelism

PyTorch DataLoader: `num_workers=N` forks N worker processes that run the `__getitem__` concurrently. Typical N = number of CPU cores per GPU (~8-16). More workers = more memory + more file handles.

## 7. Checkpointing

### 7.1 Why checkpointing is hard

A 70B model in mixed-precision training has:
- FP16 weights: 140 GB
- FP32 optimizer states (Adam has 2 moments): 560 GB
- FP32 master weights: 280 GB
- **Total per full checkpoint: 980 GB**

For a 400B model: ~5.6 TB per checkpoint.

At 10 GB/s write per node, writing one checkpoint takes 100s on 8 nodes (or longer if synchronized writing contends for bandwidth). If you checkpoint every hour, you lose ~3% of your step time to checkpointing alone.

### 7.2 Synchronous checkpointing

All ranks call `torch.save` on their shard, write to shared storage, then `dist.barrier()`. Simple, correct, slow.

### 7.3 Asynchronous checkpointing (state of the art)

**PyTorch Distributed Checkpoint (DCP):** asynchronously saves; compute continues. Checkpoint is uploaded in the background.

**Sharded checkpoints:** each rank writes its shard; metadata file lists shards. No cross-rank coordination at save time.

**Hierarchical:** write to RAM-disk → stage out to NVMe → stage to parallel FS → long-term to object store. Fastest commit to a resilient tier.

Example write time budget with DCP:
- RAM copy: 1-2 s
- NVMe write (async): 30 s in background
- Compute is stalled only for the RAM copy step

### 7.4 Checkpoint consolidation

Sharded checkpoints aren't portable across different parallelism configurations. You may need to consolidate (read all shards, concat/merge, write single file) for publishing or for changing training topology. Tools: `torch.distributed.checkpoint.save_state_dict`, `fairscale.checkpoint_utils`.

### 7.5 Async-safe resumption

A checkpoint that's mid-upload must not be loaded. Convention: write `checkpoint_0123/` atomically, then create `checkpoint_0123.DONE` marker file. Resume logic looks for the highest DONE marker.

## 8. Loading Patterns in Inference Frameworks

### 8.1 vLLM

vLLM's `Executor` handles weight loading via `ModelLoader`. Steps:
1. Discover model on disk (`~/.cache/huggingface/hub/...`)
2. Initialize TP groups via NCCL
3. Each TP rank loads its shard slice (column-wise or row-wise depending on layer)
4. Load into GPU via `.to(device)` — PyTorch handles the H2D copy
5. Optional: sharded loading (`--load-format sharded`) where each rank reads only its portion from disk

For large models, sharded loading is critical — otherwise every TP rank reads the full file, wasting NVMe BW.

### 8.2 TensorRT-LLM

Requires a build step that compiles the model into a hardware-specific engine file (.plan). The .plan is then loaded via `tensorrt.Runtime().deserialize_cuda_engine`. Loading is fast because kernels are pre-compiled; the trade is a 5-30 minute build step per hardware/model combination.

### 8.3 SGLang

Similar to vLLM; uses safetensors with sharded loading. Adds specific support for multi-LoRA hot-swapping without full reload.

## 9. Weight Streaming for Huge Models

When a model doesn't fit in GPU HBM even with quantization, modern systems stream weights from CPU on-demand.

### 9.1 DeepSpeed ZeRO-Infinity

Partitions weights, gradients, and optimizer states across GPU/CPU/NVMe. Each layer's weights stream in from CPU before compute; spill back after. Throughput is severely bandwidth-limited but enables training 100B+ models on commodity hardware.

### 9.2 FlexGen (inference)

Pioneered weight offloading for batch inference of very large models (e.g., OPT-175B on a single GPU). Weights streamed from CPU. Only practical when you have long batch processing where per-token latency is unimportant.

### 9.3 UVM (Unified Virtual Memory)

`cudaMallocManaged` allocates memory accessible from both CPU and GPU. Page faults trigger automatic migration. Simple API but unpredictable performance — pages can thrash.

## 10. Real-World Scenarios and Numbers

### 10.1 Inference cluster cold start

A new inference replica scales up for a 70B model.

- S3 pull: 140 GB at 10 Gbps = 112 s (worst case; typically 30-60 s with range requests and multi-connection)
- Load into CPU: 20 s from NVMe
- Load into GPU (8× TP): parallel 2 s
- Warmup pass: 5-10 s (JIT compilation, CUDA graph capture)
- **Total cold start: ~2-3 minutes**

Mitigations:
- Pre-populate NVMe on candidate nodes
- Use init containers to pre-download
- Keep a "warm pool" of idle replicas

### 10.2 Training cluster checkpoint

A 400B model training on 512 GPUs, checkpointing every hour.

- Per-rank write: 5.6 TB / 512 ≈ 11 GB/rank
- Parallel write to Lustre at 100 GB/s aggregate: 11 GB × 512 / 100 GB/s ≈ 56 s synchronous
- With DCP async: ~1 s foreground, 60 s background
- Cost: ~1.5% of step time if async; ~15% if sync

### 10.3 Disaggregated serving KV cache transfer

Prefill on node A finishes a 128K context request (40 GB KV for Llama-70B). Must transfer to decode pool.

- Local NVLink (same node): 40 / 900 ≈ 44 ms
- Cross-node NDR: 40 / 50 ≈ 800 ms — unacceptable for TTFT SLA
- Layer-streaming overlapped with prefill: effective overhead ~0

For long contexts, cross-node KV transfer is impractical without layer-streaming or NIXL's multi-rail.

## 11. Common Interview Questions on Storage and Loading

**Q: Why is safetensors preferred over pickled checkpoints?**
A: (1) Safety — pickle allows arbitrary code execution on load, a supply-chain attack vector. (2) Speed — safetensors is memory-mappable; pickle requires parsing Python objects. (3) Cross-language — safetensors has a simple binary format with C/Rust/Go bindings, while pickle is Python-only.

**Q: What's GPUDirect Storage and when does it help?**
A: GDS enables NVMe → GPU HBM direct transfer, skipping CPU memory. Helps when: (a) you're bottlenecked by CPU memory bandwidth (common when loading 100 GB+ models), (b) you need to free CPU memory for other uses, (c) you're doing many concurrent loads that would thrash the page cache.

**Q: Your model-loading on a fresh pod takes 3 minutes. Walk me through how to reduce it.**
A: (1) Profile — is it network-bound, disk-bound, or CPU-bound? (2) If network-bound: pre-pull weights into NVMe caches on candidate nodes; use multi-part S3 downloads (e.g., 64 parallel range requests). (3) If disk-bound: consider GDS to skip the CPU bounce; multiple NVMe drives in RAID0 for parallel reads. (4) If CPU-bound: shard the safetensors file so each TP rank reads its own portion; avoid `.cpu()` copies. (5) JIT/graph capture: do it once and cache CUDA graphs on disk.

**Q: How do you checkpoint a 400B model without stalling training for minutes?**
A: Use asynchronous sharded checkpointing (e.g., PyTorch DCP). Each rank snapshots its shard to a pinned CPU buffer in <2 s, then uploads to shared storage in the background while compute resumes. Atomic `DONE` markers protect against partial checkpoints on crash. Tier: RAM → local NVMe → parallel FS → object store.

**Q: What's the difference between Lustre and WekaFS for AI workloads?**
A: Lustre was built for HPC (few large files, sequential writes). It has a single MDS which becomes a metadata bottleneck for many small files — typical of training dataloaders. WekaFS distributes metadata and runs on NVMe with SPDK userspace, hitting 100 GB/s+ aggregate and handling AI's small-file + checkpoint-burst mix well. WekaFS costs significantly more per TB.

**Q: How does prefix caching interact with model loading?**
A: Prefix caching stores already-computed KV blocks for recurring prompts (system prompts, RAG contexts). It's separate from model weight loading — loading happens once at pod startup, and prefix cache persists in GPU HBM (or offloaded to CPU) across requests. Some systems also persist prefix cache to disk on shutdown for warm restart.

**Q: What are the main hazards of async checkpointing?**
A: (1) Non-atomic directories — need DONE markers. (2) Memory pressure — the CPU snapshot buffer can be huge (model size × number of replicas per host). (3) Network contention — if checkpoints overlap with training traffic, both slow down; use QoS or separate fabric. (4) Stale snapshots — if a checkpoint hasn't been durably committed when failure occurs, you restart from an older good one.

**Q: Why do pods for large models take so long to become Ready?**
A: Three main reasons: (1) Image pull — 20+ GB container images with CUDA + PyTorch + framework. (2) Model weight load — 140 GB to download and deserialize for 70B. (3) JIT warmup — PyTorch `torch.compile`, CUDA graph capture, NCCL initialization. Each is 30-60 s; total ~2-3 minutes. Mitigations: pre-pulled images, shared NVMe cache, CUDA graph cache files, warm-pool replicas.
